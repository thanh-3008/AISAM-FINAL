# US-42 - Tự động đăng bài theo lịch

## 1. User Story

**Là** hệ thống,
**tôi muốn** background worker xử lý schedule đến hạn để publish bài tự động,
**để** người dùng không cần can thiệp thủ công vào thời điểm đăng bài đã lên lịch.

---

## 2. Mục tiêu

Cung cấp background worker (`ScheduledPostingBackgroundService`) chạy định kỳ mỗi 30 giây, quét các ContentCalendar records có `Status = Pending` và `ScheduledAt <= now`, thực hiện publish qua `ContentService.PublishAsync`, cập nhật trạng thái schedule, tạo notification tương ứng. Feature này đảm bảo bài đăng được xuất bản đúng giờ mà không cần người dùng online.

---

## 3. Phạm vi

### Trong phạm vi

- Background service chạy vĩnh viễn khi app BE khởi động (`ScheduledPostingBackgroundService`).
- Quét mỗi 30 giây các schedule đến hạn (`GetDueSchedulesAsync`).
- Xử lý theo batch (tối đa 20 schedules mỗi lần chạy).
- Lock schedule: đặt `Status = Processing` trước khi publish → tránh xử lý trùng.
- Gọi `ContentService.PublishAsync` cho mỗi schedule.
- Cập nhật kết quả:
  - Thành công → `Status = Completed`, `ExecutedAt = now`.
  - Thất bại → `Status = Failed`, `AttemptCount += 1`, `LastError = error message`.
- Tạo notification cho cả success và failure (type `SystemUpdate`).
- Dev-only trigger endpoint: `POST /api/dev/scheduler/run-now` (chỉ trong Development).
- Log errors để host không crash.

### Ngoài phạm vi

- Recurring schedule (lặp lại nhiều lần): deferred (BE có `RepeatTypeEnum` nhưng worker chưa xử lý).
- Retry schedule thất bại tự động: deferred (hiện tại chỉ tăng attempt count, không retry).
- Websocket/SignalR real-time push: deferred (FE polling notification).
- Email notification khi publish: deferred.
- Cancel schedule đang Processing: không hỗ trợ.
- Manual trigger từ FE: chỉ có dev trigger (ko cho production).

## 4. Actor

- **Chính:** Background worker (`ScheduledPostingBackgroundService`), Backend API (`ContentService.PublishAsync`, `FacebookProvider`).
- **Phụ:** User Web App (frontend — nhận notification kết quả qua polling US-36), Facebook Graph API, Database (`ContentCalendar`, `Notification`, `Post` records).

---

## 5. Tiền điều kiện

- BE application đang chạy (worker tự động start khi host starts).
- Ít nhất một schedule record có `Status = Pending` và `ScheduledAt <= DateTime.UtcNow`.
- Content và Integration tương ứng còn hợp lệ (chưa bị soft-delete).
- Facebook page token còn hạn hoặc BE tự động refresh được.
- User còn post quota.

---

## 6. Luồng xử lý chính

### 6.1 Worker loop (mỗi 30 giây)

1. Worker chạy `RunDueSchedulesAsync(batchSize: 20)`.
2. Repository query: `SELECT * FROM content_calendar WHERE status = 0 (Pending) AND scheduled_at <= @now AND is_deleted = false ORDER BY scheduled_at ASC LIMIT 20`.
3. Với mỗi schedule trong kết quả:
   a. Set `Status = Processing`, save.
   b. Gọi `ContentService.PublishAsync(contentId, integrationId, profileId)`.
   c. Nếu success → `Status = Completed`, `ExecutedAt = now`.
   d. Nếu fail → `Status = Failed`, `AttemptCount += 1`, `LastError = message`.
   e. Tạo notification record.
4. Return `SchedulerRunResultDto { ScannedCount, SuccessCount, FailedCount }`.
5. Chờ 30 giây, lặp lại.

### 6.2 Notification được tạo

Sau mỗi lần xử lý schedule, worker tạo notification:
- **Success**: title "Scheduled publish succeeded", message "Content {contentId} was published successfully.", type `SystemUpdate`.
- **Failure**: title "Scheduled publish failed", message = error message, type `SystemUpdate`.
- Cả hai đều có `TargetId = scheduleId`, `TargetType = "content_schedule"`.

### 6.3 Kết quả hiển thị trên FE

1. **Schedules list** (US-41): schedule chuyển từ Pending → Processing → Completed/Failed.
2. **Post history** (US-35): nếu success, Post record được tạo, xuất hiện trong posts list.
3. **Content status**: nếu success, content chuyển thành `Published`.
4. **Notification** (US-36/US-37): user nhận notification "Scheduled publish succeeded/failed" qua bell polling.

### 6.4 Dev trigger (Development only)

1. Developer gọi `POST /api/dev/scheduler/run-now`.
2. Worker chạy ngay lập tức (thay vì chờ 30 giây).
3. Trả về `SchedulerRunResultDto`.
4. Endpoint này chỉ available trong Development (filter `[DevelopmentOnly]`).

## 7. Luồng ngoại lệ

| Mã | Trường hợp | Kết quả mong đợi |
| --- | --- | --- |
| EX-01 | Không có schedule đến hạn | Worker không làm gì, chờ 30 giây. |
| EX-02 | Content hoặc Integration bị soft-delete | `PublishAsync` trả lỗi; schedule → Failed, tạo notification fail. |
| EX-03 | Facebook token hết hạn, refresh thất bại | `PublishAsync` fail; schedule → Failed, notification "token expired". |
| EX-04 | Hết post quota | `PublishAsync` trả 403; schedule → Failed, notification "quota exceeded". |
| EX-05 | Worker crash vì exception ngoài ý muốn | `try/catch` outer → log error, không crash host, tiếp tục loop. |
| EX-06 | Schedule đang Processing (đã bị worker khác pick) | Worker chỉ query Pending schedules, không ảnh hưởng. |
| EX-07 | Content đã Published trước đó | `PublishAsync` BE trả lỗi; schedule → Failed. |

## 8. Quy tắc nghiệp vụ

| Mã | Quy tắc |
| --- | --- |
| BR-01 | Worker chạy 30 giây một lần, không configurable qua API. |
| BR-02 | Batch size mặc định 20 schedules mỗi lần. |
| BR-03 | Schedule được lock bằng cách set `Status = Processing` trước publish → tránh double-publish. |
| BR-04 | `AttemptCount` tăng mỗi lần thất bại, không giới hạn số lần retry (hiện tại chỉ fail 1 lần, không retry tự động). |
| BR-05 | Notification được tạo cho cả success và failure — user nhận qua bell (US-36). |
| BR-06 | Worker không retry schedule thất bại — user phải manual edit và resave (US-41). |
| BR-07 | Worker không làm việc với soft-deleted records (`IsDeleted = false`). |
| BR-08 | Dev trigger `POST /api/dev/scheduler/run-now` chỉ khả dụng trong Development environment. |

## 9. API Contracts

### 9.1 Dev Scheduler Trigger (Development only)

```
POST /api/dev/scheduler/run-now
```

#### Headers
```http
Authorization: Bearer <access-token>
X-Profile-Id: <owned-profile-guid>
```

#### Response (200 OK)
```json
{
  "success": true,
  "statusCode": 200,
  "message": "Scheduler run completed successfully.",
  "data": {
    "scannedCount": 5,
    "successCount": 3,
    "failedCount": 2
  },
  "timestamp": "2026-06-03T15:00:00Z"
}
```

#### Response (404 — not in Development)
```json
{
  "success": false,
  "statusCode": 404,
  "message": "Not found.",
  "data": null,
  "timestamp": "2026-06-03T15:00:00Z"
}
```

### 9.2 Notification tạo bởi Worker (ví dụ)

```json
{
  "id": "notification-guid",
  "type": "SystemUpdate",
  "title": "Scheduled publish succeeded",
  "message": "Content abc-123 was published successfully.",
  "isRead": false,
  "createdAt": "2026-06-10T15:01:00Z"
}
```

```json
{
  "id": "notification-guid-2",
  "type": "SystemUpdate",
  "title": "Scheduled publish failed",
  "message": "Facebook token expired. Please reconnect.",
  "isRead": false,
  "createdAt": "2026-06-10T15:01:00Z"
}
```

> FE không gọi API worker trực tiếp. Các API liên quan đã được định nghĩa trong US-36 (notifications), US-41 (schedules list), US-35 (posts list).

## 11. Responsive States

| State | Mô tả |
| --- | --- |
| **Worker idle** | Không có schedule đến hạn; chờ 30 giây. |
| **Worker processing** | Schedule chuyển Processing trong DB; FE thấy qua lần refresh/list fetch tiếp theo. |
| **Worker success** | Schedule → Completed, Post created, Notification tạo. |
| **Worker failure** | Schedule → Failed, AttemptCount +1, Notification lỗi. |
| **Dev trigger called** | Worker chạy ngay, trả về result stats. |

## 12. Acceptance Criteria

### AC-01 - Worker chạy 30 giây

**Given** BE app đang chạy
**When** 30 giây trôi qua
**Then** worker gọi `GetDueSchedulesAsync(DateTime.UtcNow, 20, ct)`.

### AC-02 - Schedule thành công

**Given** có schedule Pending đến hạn
**When** worker xử lý
**Then** schedule chuyển Processing → Completed
**And** `ExecutedAt` được set
**And** Post record được tạo
**And** Content chuyển Published.

### AC-03 - Schedule thất bại

**Given** có schedule Pending đến hạn nhưng publish fail
**When** worker xử lý
**Then** schedule chuyển Failed
**And** `AttemptCount` +1
**And** `LastError` được set.

### AC-04 - Notification được tạo

**Given** worker xử lý schedule
**Then** notification record được tạo với type `SystemUpdate`.

### AC-05 - Dev trigger

**Given** environment là Development
**When** gọi `POST /api/dev/scheduler/run-now`
**Then** worker chạy ngay
**And** trả về `SchedulerRunResultDto`.

### AC-06 - Worker không crash host

**Given** worker gặp exception
**Then** exception được log
**And** worker loop tiếp tục.

### AC-07 - Không double-publish

**Given** schedule đã chuyển Processing
**When** worker chạy lần tiếp theo
**Then** schedule không bị pick (vì status ≠ Pending).

## 13. Gợi ý Implementation

### Backend - .NET 8 — ĐÃ IMPLEMENT

> Backend đã implement đầy đủ:
> - `ScheduledPostingBackgroundService` — `BackgroundService`, loop 30 giây, gọi `RunDueSchedulesAsync`.
> - `ScheduledPostingService` — query due schedules, set Processing, gọi `ContentService.PublishAsync`, cập nhật kết quả, tạo notification.
> - `DevSchedulerController` — `POST /api/dev/scheduler/run-now` (Development only).
> - `SchedulerRunResultDto` — ScannedCount, SuccessCount, FailedCount.
> - Notification tạo tự động với type `SystemUpdate`.
>
> **Không cần thêm BE work.**

### Frontend — Chỉ dev-trigger UI (optional)

```typescript
// components/dev/dev-scheduler-panel.tsx — chỉ render trong development
"use client";

import { useState } from "react";
import { apiRequest } from "@/lib/api/fetcher";

interface SchedulerResult {
  scannedCount: number;
  successCount: number;
  failedCount: number;
}

export function DevSchedulerPanel() {
  const [result, setResult] = useState<SchedulerResult | null>(null);
  const [isRunning, setIsRunning] = useState(false);
  const [error, setError] = useState<string | null>(null);

  if (process.env.NODE_ENV !== "development") return null;

  const handleRunNow = async () => {
    setIsRunning(true);
    setError(null);
    try {
      const res = await apiRequest<SchedulerResult>("/api/dev/scheduler/run-now", {
        method: "POST",
        auth: true,
      });
      setResult(res);
    } catch (err) {
      setError((err as Error).message);
    } finally {
      setIsRunning(false);
    }
  };

  return (
    <div className="rounded-lg border border-amber-200 bg-amber-50 p-4 text-sm">
      <h3 className="mb-2 font-semibold text-amber-800">🔧 Dev Panel — Scheduler</h3>
      <div className="flex items-center gap-3">
        <button
          onClick={handleRunNow}
          disabled={isRunning}
          className="rounded-md bg-amber-600 px-3 py-1.5 text-xs font-medium text-white transition-colors hover:bg-amber-700 disabled:opacity-50"
        >
          {isRunning ? "Running..." : "Run Now"}
        </button>
        {result && (
          <span className="text-xs text-amber-700">
            Scanned: {result.scannedCount} | ✅ {result.successCount} | ❌ {result.failedCount}
          </span>
        )}
        {error && <span className="text-xs text-red-600">{error}</span>}
      </div>
    </div>
  );
}
```

## 15. Definition of Done

- [ ] Worker chạy tự động 30 giây/lần.
- [ ] Query due schedules Pending và `ScheduledAt <= now`.
- [ ] Lock schedule bằng Processing trước publish.
- [ ] Publish thành công → Completed + ExecutedAt + Post record.
- [ ] Publish thất bại → Failed + AttemptCount + LastError.
- [ ] Notification tạo cho success và failure (type `SystemUpdate`).
- [ ] Worker không retry schedule thất bại.
- [ ] Worker không crash host khi exception.
- [ ] Dev trigger `POST /api/dev/scheduler/run-now` (Development only).
- [ ] `[DevelopmentOnly]` attribute bảo vệ dev trigger khỏi production.
- [ ] Schedules list (US-41) hiển thị trạng thái mới.
- [ ] Notifications (US-36) hiển thị kết quả worker.
- [ ] Posts history (US-35) hiển thị post mới từ auto-publish.
- [ ] Content detail hiển thị status Published.
- [ ] Unit test và integration test pass.
- [ ] Không có regression trên Schedule, Content, Post, Notification modules.
